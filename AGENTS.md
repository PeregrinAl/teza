# Инструкции для агентов разработки

## Назначение и этап работы

- Название проекта — `teza`, в нижнем регистре.
- Этот репозиторий — обложка: общая документация и договорённости компонентов.
  Прикладной код предназначен для `teza-backend` и `teza-web`.
- Реализация backend начата в соседнем `teza-backend`; пользователь разрешил
  разработку и запросил README с запуском для Windows, macOS и Linux.
  В репозиторий-обложку прикладной код не добавлять.
- Новые репозитории создаст пользователь. Не создавать их от его имени.
  После сообщения об их создании проверить доступ, добавить ссылки и убрать
  статус «Планируется» из README. До проверки не выдавать их за существующие.
- Использовать существующие checkout. Не создавать Git worktree без явной просьбы.

## Документация и передача работы

- README, спецификация и архитектура предназначены для исследователей,
  любителей и программистов. Не вставлять туда пересказ переписки, поручения
  агенту, ограничения текущей сессии или фразы о «владельце проекта».
- Операционные заметки и правила передачи между агентами хранить здесь.
  Решения о поведении продукта — в соответствующей документации.
- Исходное ТЗ предоставлено файлом «Вставленный текст.txt». Последующие
  уточнения пользователя имеют приоритет над ним. FR/AC — устойчивые ссылки;
  при изменении смысла обновлять требования и критерии согласованно.
- Последние уточнения: минимальный объём достаточного кода; Java остаётся;
  заменяемый AI; публичный ресурс с возможной монетизацией доступа к разборам;
  обезличенные и переформулированные аргументы, отдельные маркеры для ошибок,
  риторики и фрагментов без аргумента. Без профилей участников и обогащения
  сведений о них внешними данными. Публичность уточнена пользователем явно:
  не трактовать проект как исключительно личную закрытую базу.
- Инструкции не зависят от продукта или модели агента. В конце задачи сообщать,
  какие файлы изменены, что проверено и какие решения ещё открыты.

## Принципы реализации

- KISS, DRY, SOLID и YAGNI: реализовывать текущий сценарий, не строить
  инфраструктуру, пустые модули и универсальные абстракции на будущее.
- Интерфейсы нужны на реальных границах, прежде всего для заменяемого AI.
  Не создавать интерфейс для каждого класса или общий framework из пары функций.
- Не менять подтверждённые данные при смене AI-движка, повторном анализе
  или смене агента-разработчика. Применять предложения через доменную валидацию.
- Не начинать сбор реальных внешних дискуссий в рамках документационной задачи.
  Не сохранять персональные данные участников дискуссий и неочищенные тексты.
  Ключи не помещать в Git; разрешения на использование не выдумывать.
- Не объявлять текст анонимным только потому, что удалены имена. Правила
  допустимости корпуса и ограничений статистики — в `docs/RESEARCH-DATA.md`.
